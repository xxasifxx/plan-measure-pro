## Pass A — commit clustering with multi-attribution

- Walk commits in chronological order.
- Each commit's `pathTags[]` (top 6) are bucket keys. Primary tag → primary attribution. Remaining tags → secondary attribution (separate live activity per tag bucket).
- Within a bucket: score against live activities (idle <14d) by `0.4*jaccard(tokens) + 0.6*jaccard(files)`. Threshold 0.15 to merge; otherwise mint a new activity. Fallback to most-recent-in-bucket prevents runaway fragmentation.
- One commit therefore yields 1..N rows in `commit_activity` — one primary + N-1 secondary contributions.

Current: **1.52 activities per commit** (mean), **378 / 967** commits have ≥1 secondary attribution.

## Pass B — leaf-driven synthesis

- After Pass A, every WBS leaf is checked. If still empty, a stub activity (`origin: future-risk`, `evidence.reason: leaf-unattributed`) is minted so each WBS entry has ≥1 activity.
- Open criteria (verdict ≠ implemented/shipped/verified) on leaves with no git activity become `future-verification-gap` activities. Mostly absorbed by Pass A this run because leaf criteria are catalog-only.

## Predecessor inference (4 signals)

| Signal | Weight | Source |
|---|---|---|
| Same-leaf temporal ordering | 0.30 | adjacent activities under one leaf, sorted by `time_window.first` |
| Commit-token cues ("after", "depends on", "now that", …) | 0.25 | activity `name` regex + token overlap with siblings |
| L4 cross-stream links | 0.30 | `intent-leaves.json.cross_stream_links` mapped onto our leaves |
| Leaf-criterion authoring order | 0.40 | criteria within a leaf, matched to activity names by token overlap |

Edges merge by `(pred, succ)`; confidences sum (capped at 1.0). Edges below 0.30 land in `relationships.rejected.json`. Cycles broken by dropping the lowest-confidence edge along the cycle until acyclic.

Current: **169 accepted, 52 rejected, 0 cycles needed breaking** (the four signals are sparse enough that cycles are rare).

## State vector

`state.json` keeps four independent dimensions so the user vocabulary stays expressive:

```
lifecycle:  planned | in-flight | paused | dormant | shipped | abandoned
blocking:   { kind: successor-missing | external | decision | none, note }
health:     { dormancy_days, marketing_debt_count, verification_gap_count }
visibility: quiet | normal | loud
```

Examples:
- **dormant-but-needed** = `lifecycle=dormant|paused` + `downstream_count>0` (or marketing_debt > 0)
- **awaiting-successor** = `lifecycle=paused` + `blocking.kind=successor-missing`
- **paused-pending-decision** = `lifecycle=paused` + `blocking.kind=decision`
- **abandoned-but-loud** = `lifecycle=abandoned` + `visibility=loud`

Lifecycle is derived against a fixed data date of `2026-05-29T19:30:00Z`. Thresholds: quiet ≤30d, dormant ≤60d.
